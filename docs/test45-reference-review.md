**Почему референс ощущается естественнее**

- Ритм неоднородный: длинное наблюдение за действием, короткие перечисления.
  Средняя частота склеек почти идентична test45; ускорять всё не нужно.
- Материал обычно показывает конкретное действие: встреча, игра, еда,
  лестница, дорога, плавание. Зрителю редко нужно расшифровывать метафору.
- Внутри кадра есть движение объекта, ручной камеры, развитие ситуации.
  Это важнее искусственного приближения неподвижной картинки.
- Обычные склейки преобладают; замысловатые переходы не являются причиной качества.
- Референс использует и заполнение вертикального экрана, и горизонтальные
  видео с размытой подложкой. Это сохраняет действие/контекст. Full-screen
  9:16 test45 оставлен согласно требованиям пользователя.
- В обоих роликах белые контрастные субтитры с чёрной обводкой и короткими
  карточками. У референса преимущественно одно слово; позиция около
  середины/нижней середины меняется вместе с компоновкой. Текст test45
  расположен в сходной области. Перенастройка шрифта сейчас менее
  обоснованна, чем исправление тайминга.
- В референсе фото и стоп-кадр имеют отдельную функцию. Однако переносить
  долю видео на исторический сюжет буквально нельзя: нужна фактическая точность.
- Повторы и стоп-кадр референса не предлагаются как новые fallback-механизмы.

**Где это находится в коде и минимальная последовательность**

| Различие | Ответственные модули | Решение |
|---|---|---|
| Тайминг слов | transcript.py → models.py/io.py → renderer.py | Этап 1: сохранить реальные времена; проверить независимо от поиска |
| Смысловые границы | broll_planner.py: prompt и _normalize_start_indices | Следующий этап после живого A/B |
| Семантика и приоритет видео | broll_planner.py, gemini_ai.py, stock_video.py; reference_style.py в legacy fallback | Проверить варианты запросов/кандидатов на том же тексте до смены правил |
| Плавность фото, crop видео | renderer.py: _image_filter, _render_reference_video | Сохранить текущую реализацию на первом этапе |
| Покрытие, rescue, уникальность | assets.py, cli.py:_resolve_and_repair, material_brain.py, qc.py | Сохранить и проверять на реальном результате |

В planner есть конкретная причина для будущего этапа: Gemini получает слова
с индексами, но не их таймкоды; затем нормализатор режет промежутки >3,5 с
по ближайшему слову к временному ориентиру. Новый участок наследует
описание ближайшего предыдущего beat. Это может создавать лишнюю склейку
без нового визуального смысла. Будущий минимальный эксперимент: передавать
таймкоды в prompt и проверять осмысленные границы вместо нейтрального
midpoint. Не менять это одновременно с caption timing.

**Что изменено сейчас**

Ровно одна поведенческая область: синхронизация субтитров.

- Scene хранит caption_words с исходными абсолютными start/end/text.
- Оба планировщика сохраняют исходные Word, JSON переносит их до render.
- Карточки используют начало первого и конец последнего слова. Сохраняется
  максимум два слова; через паузу >0,18 с слова не объединяются.
- Небольшие перекрытия времён Whisper не создают перекрытия карточек.
- Для старых JSON, несовпавшего текста и некорректных времён остаётся
  прежнее взвешивание по длине слова. Стиль и движение не менялись.
- render --transcript позволяет взять оригинальный transcript.json и
  проверить новые субтитры на сохранённом materialized plan. Несовпадение
  текста останавливает такой явный A/B-запуск до рендера.

Полный набор исходных тестов: stable-test45 — 32 passed / 11 failed.
После изменения: те же 11 исходных падений, плюс новые проходящие проверки.
Старые тесты местами ожидают прежние правила повторов и выбора материалов;
они не переписывались под этот этап.

В среде нет ключей Gemini/Pexels/Pixabay и оригинальной work-папки test45
(transcript.json, materialized plan, исходные assets). Поэтому новый
end-to-end ролик с поиском/Gemini не создан и его превосходство не заявляется.
Синхронизация проверена на известных контрольных временах; качество ASR
на конкретной озвучке всё ещё влияет на результат.

Также существующий QC не является абсолютной гарантией результата:
inspect_plan проверяет преимущественно метаданные/пути, а renderer может
заменять повреждённый файл тёмной подложкой. Это уже было в c151cb4;
по этому этапу новых гарантий для произвольных входных файлов нет.
Реальный следующий прогон должен включать проверку готового MP4.

**PowerShell: следующий изолированный A/B**

В каталоге существующего репозитория; заменить только путь к оригинальной
папке --work-dir, использованной при создании test45. Папка и assets должны
остаться на исходных путях, записанных в JSON.

```powershell
git switch main
git pull --ff-only
python -m pip install -e .
$work45 = "C:\ПУТЬ\К\ПАПКЕ_TEST45"
video-ai render "$work45\shot_plan.materialized.json" `
  --transcript "$work45\transcript.json" `
  -o ".\test45-captions-ab.mp4" `
  --work-dir ".\work-captions-ab"
```

Этот запуск использует звук, указанный в materialized plan. В create этот
план сохраняется до audio mix: если test45 включал дополнительную музыку/SFX,
для точного сравнения звука потребуется копия плана со ссылкой на сохранённый
mixed_audio.m4a. Команда выше не пересоздаёт поиск, Gemini или визуальные QC.

Полный следующий тест после A/B, с исходной озвучкой и уже настроенными ключами:

```powershell
video-ai create ".\voice.mp3" -o ".\test45-next.mp4" `
  --work-dir ".\work-test45-next" --language ru
```

Использовать ту же озвучку и те же дополнительные флаги, что в test45
(например, --no-sfx или --semantic, если они применялись). Отдельная папка
сохраняет исходные материалы test45. Перед принятием следующего этапа:
проверить финальный JSON, qc.json, duplicate_scenes, отсутствие чёрных
кадров в готовом MP4 и вручную сравнить смысл, ритм и субтитры.
